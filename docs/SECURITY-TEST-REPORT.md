## 2. 只读改造消除的攻击面

本次改造将配置从"API + KV 可写"收敛为"代码内集中维护 + 只读下发"，从根本上消除了原架构的最大风险：

- **公开访问者添加/篡改监控项**：原 `POST/PUT/DELETE /api/monitors` 一旦鉴权配置疏漏即可被利用。现在这些接口被整体移除并返回 405，页面也无任何增删改入口，攻击面归零。
- **配置型 SSRF 的入口暴露**：原 SSRF 防护依赖"谁有 ADMIN_TOKEN 谁能配 URL"的假设；现在配置只能由有代码提交/部署权限的管理员维护，探测阶段仍对每个目标强制执行 SSRF 校验（纵深防御），双重保障。
- **探针回传污染监控列表**：ingest 现在校验目标 ID 必须存在于当前 `src/config.mjs` 配置中，已移除的旧目标无法再被写入数据。

## 3. 历史中发现并修复的问题（沿用）

### 3.1 SSRF 绕过：IPv6 字面量方括号（严重）
- **现象**：`new URL('http://[::1]/').hostname` 带方括号导致私网判断失效；IPv4-mapped IPv6 十六进制写法同样可绕过。
- **修复**：统一剥离方括号；展开 `::ffff:` 映射再判断；拒绝纯数字/十六进制混淆主机名。
- **验证**：覆盖 `127.0.0.1`、`[::1]`、`[::ffff:7f00:1]`、`2130706433`、`169.254.169.254` 等，全部拒绝。

### 3.2 告警去重失效风险：动态错误签名（中等）
- **现象**：签名拼接原始错误文本，文案波动绕过冷却窗口形成告警风暴。
- **修复**：`errorClass()` 归一化为 `timeout`/`probe-missing`/`dns`/`tls`/`network`/`http` 六类，签名为 `status + errorClass`。
- **验证**：不同文案同类别错误冷却期内只告警 1 次，切换类别后才新增通知。

### 3.3 鉴权边界：令牌中间空格（低）
- 令牌内部含任意空白即拒绝；首尾 OWS 由 HTTP 栈按 RFC 7230 剥离，不构成绕过。

## 3.4 二轮整体审计新发现并修复的问题（本轮）

本轮进行独立安全审计（静态分析 + 输入行为验证），新增修复如下：

### 3.4.1 告警发送失败仍写入冷却标记，导致故障漏报（高）
- **现象**：`src/index.mjs` 的 `dispatchAlerts()` 用 `Promise.allSettled` 吞掉所有通道错误且永不 reject，`applyIncident()` 随后无条件写入 `lastAlertAt`/`lastSignature`。一旦 Webhook/邮件端点故障，发送失败却被当成"已通知"，同类别错误在冷却期（默认 300s）内不再重试；若期间状态恢复，**该故障告警彻底丢失**。与 `demo.mjs` 的正确实现行为不一致。
- **修复**：`sendWebhook`/`sendEmail` 检查 HTTP 响应状态（非 2xx 抛错）；`dispatchAlerts` 返回成功投递通道数；仅当 `delivered > 0` 才写入冷却标记，否则保留旧标记供下一轮立即重试。两个版本行为统一。
- **验证**：新增用例模拟 Webhook 返回 500 → 首轮不写冷却标记、目标持续故障时下一轮立即重试并成功投递。

### 3.4.2 SSRF：IPv6 隧道地址内嵌内网 IPv4 可绕过（高）
- **现象**：`isPrivateIp()` 仅拦截 `::1`/`fc`/`fd`/`fe80` 等前缀，`2002:7f00:1::`（6to4 内嵌 127.0.0.1）、`64:ff9b::7f00:1`（NAT64）、Teredo `2001:0::/32` 等隧道地址均被判为公网而放行，可绕过 SSRF。
- **修复**：`isPrivateIp()` 增加 6to4 / Teredo / NAT64 内嵌 IPv4 展开判断，扩展 IPv4-mapped 的十六进制/省略写法解析，并拒绝含前导零的八进制混淆 IPv4 段；`assertPublicTarget()` 拒绝整数/十六进制/八进制混淆主机名。
- **验证**：新增用例覆盖上述隧道地址与混淆写法（全部拒绝），并确认公网 IPv6（`2001:4860:4860::8888`）不误判。

### 3.4.3 混合线路（edge+external）ingest 永不评估（中）
- **现象**：`/api/ingest` 的 `allFresh` 遍历所有线路读取 `probe:<id>:<probeId>`，但 edge 线路的结果从不写入该 KV（由 scheduled 即时探测），导致 edge+external 混合配置下 `allFresh` 恒为 false，`commitRound` 永不执行，外部回传无法即时评估/告警。
- **修复**：ingest 评估时对 edge 线路即时 `probeOnce` 补入结果，仅对 external 线路判断 KV 新鲜度。
- **验证**：新增用例确认混合线路 external 回传后立即 `evaluated=true` 并写入含两条线路结果的完整轮次。

### 3.4.4 KV 数据被污染导致接口/轮次崩溃（中，健壮性）
- **现象**：`history:*`/`events:*`/`incident:*` 读出后直接 `unshift`/`filter`/`slice`，若值被写成非数组/非对象会抛 `TypeError`，单个坏数据即可让公开 `/api/status` 返回 500。
- **修复**：新增 `asArray`/`asObject` 校验，所有 KV 读取点统一回退；告警状态用 `defaultIncident()` 补全默认字段（同时修复 `consecutiveFailures` 变 NaN 的隐患）。
- **验证**：新增用例写入非法类型后状态接口仍正常、检测轮次自动修复为数组。

### 3.4.5 公开接口回传原始异常文本（低，信息泄漏）
- **现象**：`/api/status` 的 `recentErrors.error` 直接回传原始异常文本（可能含内部主机/IP/TLS 细节）。
- **修复**：改为只返回稳定 `errorClass` 分类。前端渲染未依赖该字段，无兼容性影响。

### 3.4.6 状态接口可被缓存（低，实时性）
- **修复**：`/api/status` 增加 `Cache-Control: no-store, max-age=0`，避免浏览器/CDN 缓存导致状态延迟。

## 4. 静态扫描结果

扫描 `eval(`、`new Function`、`innerHTML`、`outerHTML`、`document.write`、`child_process`、`exec(`、`spawn(`：

- 产品源码中**零命中**。
- 唯一命中为安全测试自身的断言字符串与国内探针脚本对 `process.env` 的正常读取。
- 项目无第三方运行时依赖，供应链攻击面极小。

## 5. 残余风险与说明

| 风险 | 说明 | 缓解措施 |
|---|---|---|
| DNS rebinding（TOCTOU） | 校验时 DNS 解析与实际连接之间存在时间窗，Workers 环境无法把连接固定到已校验 IP | 禁止 IP 字面量与混淆写法、解析后校验、拒绝跟随重定向、仅 http(s) |
| 代码与变量权限 | 能提交 `src/config.mjs` 的人决定探测目标，能改告警变量的人决定通知去向 | 仓库保护分支 + 仅管理员可改 Dashboard 变量；开启 2FA 与审计日志 |
| 配置更新切换窗口 | 改监控项需重新部署；告警变量更新时 Workers 滚动更新隔离实例，极短时间内新旧配置并存 | 最终一致；关键变更可在低峰期进行 |
| 告警最终投递 | 邮件依赖 Resend、Webhook 依赖用户端点 | 工具保证按策略触发与发送，Webhook 带 HMAC 签名；建议接收方验签 |
| Demo 版本 | 阶段 A 为单文件演示 | 生产部署使用阶段 B（`src/index.mjs`，main 已指向该文件） |

## 6. 结论

在自动化覆盖范围内，UptimePulse 只读版未发现未修复的已知漏洞或逻辑漏洞。只读改造消除了"公开访问者篡改监控配置"这一根本攻击面，SSRF、XSS、告警去重失效等核心风险均有对应用例守护。二轮整体安全与逻辑审计发现并修复了 6 类问题（告警漏报、IPv6 隧道 SSRF、混合线路永不评估、KV 污染崩溃、错误信息泄漏、状态接口缓存），均已补充回归用例。当前 50 项测试全部通过并连续 6 次稳定。残余风险已如实标注并给出缓解建议。
